# Delta for Store Registry

New capability. A store is a Shopify shop the operator registered, with encrypted credentials and a verification status. Field names below are the contracts names. Log field names derived from these fields MUST avoid the redaction substrings (use `authKind`, not a name containing `credential` or `token`).

## ADDED Requirements

### Requirement: Store record and statuses

A store summary MUST have exactly these fields: `id` (UUID), `displayName`, `shopDomain` (canonical `<handle>.myshopify.com`, lower case), `shopifyShopId` (string or null), `apiVersion` (string or null), `authKind` (`static_token` or `client_credentials`), `status`, `hasCredentials` (boolean), `lastVerifiedAt` (ISO 8601 UTC string or null), `lastVerification` (snapshot object or null), `createdAt` and `updatedAt` (ISO 8601 UTC strings). `status` MUST be one of `UNVERIFIED`, `CONNECTED`, `AUTH_FAILED`, `SCOPE_MISSING`, `UNAVAILABLE`, and no other value MUST be stored or returned.

#### Scenario: Summary shape

- GIVEN a store created with a valid body
- WHEN the store is read
- THEN the summary contains exactly the fields listed above and no others

#### Scenario: Closed status set

- GIVEN a status value outside the five allowed values
- WHEN the summary schema parses it
- THEN parsing fails

#### Scenario: Unverified summary

- GIVEN a store that was never verified
- WHEN it is read
- THEN `shopifyShopId`, `apiVersion`, `lastVerifiedAt` and `lastVerification` are null and `status` is `UNVERIFIED`

### Requirement: Create is offline and starts UNVERIFIED

Creating a store MUST NOT make any outbound call. The store MUST be created with status `UNVERIFIED`, an `id` generated by the server as a random UUID (any `id` in the request body is not accepted), `hasCredentials` true, and `createdAt` equal to `updatedAt`.

#### Scenario: No outbound call on create

- GIVEN a gateway and a `fetch` that fail the test when called
- WHEN a store is created
- THEN creation succeeds and neither was called

#### Scenario: Initial state

- GIVEN a valid create request
- WHEN the store is created
- THEN `status` is `UNVERIFIED`, `id` is a UUID, and `createdAt` equals `updatedAt`

#### Scenario: Client-supplied id

- GIVEN a create body that contains an `id` field
- WHEN it is submitted
- THEN the request is rejected as invalid and no store is created

### Requirement: Display name length

`displayName` MUST be trimmed of surrounding whitespace and MUST then contain between 1 and 80 Unicode characters (code points). It does not have to be unique.

#### Scenario: Boundaries accepted

- GIVEN display names of exactly 1 and exactly 80 characters
- WHEN stores are created with them
- THEN both succeed

#### Scenario: Out of range

- GIVEN a display name that is empty, whitespace only, or 81 characters long
- WHEN a store is created with it
- THEN the request is rejected as invalid and no store is created

#### Scenario: Same name twice

- GIVEN a store named `Main shop`
- WHEN another store with a different domain is created with the name `Main shop`
- THEN creation succeeds

### Requirement: Unique canonical domain

The canonical shop domain MUST be unique across stores. Two inputs that canonicalize to the same domain (for example `Demo`, `demo.myshopify.com` and a pasted URL for that host) MUST conflict. A duplicate MUST NOT create or modify any row and MUST be reported as a conflict.

#### Scenario: Duplicate by equivalent input

- GIVEN a store with domain `demo.myshopify.com`
- WHEN a store is created with the input `https://DEMO.myshopify.com/admin/products`
- THEN creation fails with a conflict and the row count is unchanged

#### Scenario: Different domains

- GIVEN a store with domain `demo.myshopify.com`
- WHEN a store is created for `other.myshopify.com`
- THEN creation succeeds

### Requirement: Replacing credentials resets verification

Replacing the credentials of a store MUST overwrite the stored envelope, set `status` to `UNVERIFIED`, and set `shopifyShopId`, `apiVersion`, `lastVerifiedAt` and `lastVerification` to null. It MAY change the credential kind. It MUST NOT change `id`, `displayName`, `shopDomain` or `createdAt`, MUST update `updatedAt`, and MUST make no outbound call. A different domain is not changeable; the operator deletes and recreates the store.

#### Scenario: Reset after connected

- GIVEN a store with status `CONNECTED` and a snapshot
- WHEN its credentials are replaced
- THEN `status` is `UNVERIFIED` and the four verification fields are null

#### Scenario: Kind change

- GIVEN a store with kind `static_token`
- WHEN its credentials are replaced with a `client_credentials` payload
- THEN `authKind` is `client_credentials`

#### Scenario: Immutable fields

- GIVEN a store
- WHEN its credentials are replaced
- THEN `id`, `displayName`, `shopDomain` and `createdAt` are unchanged and `updatedAt` is not earlier than before

### Requirement: Hard delete

Deleting a store MUST remove its row, including the stored envelope, in one operation. Nothing MUST remain that identifies the store or its credentials. Deleting an unknown store MUST report not found.

#### Scenario: Row removed

- GIVEN a store with an envelope
- WHEN it is deleted
- THEN the `store` table has no row for it and a read reports not found

#### Scenario: Re-create after delete

- GIVEN a deleted store with domain `demo.myshopify.com`
- WHEN a store for the same domain is created
- THEN creation succeeds with a new `id`

#### Scenario: Unknown store

- GIVEN no store with a given id
- WHEN it is deleted
- THEN the operation reports not found

### Requirement: No credential or envelope in any output

No API response, summary, log line, error body or snapshot MUST contain a credential, a token, an envelope, a masked suffix of any of them, or the length of a secret. A summary MUST expose credentials only through the boolean `hasCredentials`.

#### Scenario: Summary has no secret fields

- GIVEN a store created with canary secrets
- WHEN the summary is serialized
- THEN it contains no canary substring, no `sb1.` envelope prefix, and only the boolean `hasCredentials`

#### Scenario: Summary after replace

- GIVEN a store whose credentials were replaced with new canary secrets
- WHEN it is read
- THEN neither the old nor the new canary appears in the output
